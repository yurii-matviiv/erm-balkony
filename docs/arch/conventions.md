# Архітектурні конвенції

> Частина документації ERM. Індекс і навігація: [CLAUDE.md](../../CLAUDE.md). Читай цей файл, лише якщо задача стосується теми вище.

## Filament: два паттерни ресурсів

1. **Повний ресурс зі сторінками** (`UserResource`, `ClientResource`) — стандартні `index`/`create`/`edit` routes.
2. **Модальний ресурс** (`SupplierResource`, `VacancyResource`, `VacancyApplicationResource`) — у `getPages()` зареєстрована **тільки** `index`. Filament тоді сам відкриває `CreateAction`/`EditAction` як модалку замість переходу на сторінку. Обраний свідомо для простих сутностей, де повноцінна сторінка — оверкіл (за прямим запитом користувача). Дочірні колекції (контакти/платіжні профілі постачальника) редагуються через `Repeater::make(...)->relationship()` прямо в тій же модалці.

Для "заявка на вакансію" обрано ще один паттерн: `Select::make('candidate_id')->relationship(...)->searchable([...])->createOptionForm([...])` — пошук існуючого кандидата за телефоном/ПІБ або створення нового прямо в модалці. Це і є той "чи кандидат вже є в базі" чек, без жодної кастомної JS/reactive-логіки.

## Зображення (логотипи тощо) — через git

Зображень у системі мало, тому вони лежать у `public/images/` і комітяться в репозиторій — на хостинг потрапляють звичайним `git push` разом з кодом (окремого завантаження файлів по FTP не потрібно). Каталог НЕ в `.gitignore`. Логотип сайту (`balkony-vikna.kyiv.ua/image/company/logo/logo-2025.svg`) розрізано на дві частини: `logo-mark.svg` (4 прозорі квадрати з тонким синім контуром (#4aa3df, як іконки меню), без заливки) — інлайниться в `AppServiceProvider` як іконка кнопки згортання/розгортання сайдбару (`FilamentIcon::register` замість стрілок), (1.5rem). У шапці сайдбару — лише текст "ERM ВІКНА" (font-weight 300) з відступом 15px зліва (`brandLogo()` у `AdminPanelProvider::configureCommon()`); напис "ВІКНА" (`logo-vikna.svg`) тимчасово не використовується. Сайдбар повністю чорний. `logo-btv.png` і `logo-icon.svg` — старі спроби, більше не використовуються. Якщо зображень стане багато або з'являться користувацькі завантаження — це вже `storage`, а не `public/images`.

## Як переносити сторінку зі старої CRM (обов'язковий порядок)

Порівняння лише скріншотів НЕ достатньо — приховану логіку (хто що бачить, фільтри, права, побічні дії) видно тільки в коді. Для кожної сторінки менеджера: (1) прочитати старий контролер у `dev.ERM-btv/app/Controllers/*` і модель у `app/Models/*` (read-only): які записи вибираються, чи є фільтр за користувачем/роллю, які дії і права; (2) порівняти зі скріншотом старої сторінки; (3) лише тоді будувати. Зафіксовані факти: **Ліди** — фільтр сидить НЕ в SQL (`Enquiry::getEnquiries` бере всі), а в шаблоні `Views/Enquiry/index.php`: рядок виводиться лише якщо `manager_name == поточний користувач` АБО лід ще нікому не призначений (роль Адмін бачить усе); чужі ліди — порожні рядки. Нові (непризначені) бачать усі, прийнятий лід зникає для інших. «Прийняти» = обрати себе менеджером ліда; лічильник необроблених = `who_added_user_id IS NULL AND date > 2024-01-01`. У новій системі це `LeadResource::getEloquentQuery()` (панель менеджера), бейдж у меню і дія «Прийняти заявку» на сторінці ліда; **Замовлення** — менеджер бачить тільки свої (`manager_id`).

## Шрифти та іконки (швидкість)

Шрифт — Roboto Variable, САМОСТІЙНО хоститься в `public/fonts/roboto/` (woff2 лише кирилиця + латиниця, ~65 KB, ліцензія OFL; джерело — npm `@fontsource-variable/roboto`; підключено через `->font('Roboto Variable', url: …, provider: LocalFontProvider::class)` у `configureCommon()`): чіткий, однаковий на всіх пристроях, без запитів до Google/Bunny. Спроба з системним Segoe UI виявилась замалою/світлою на вигляд. Базовий розмір збільшено (`html{font-size:106.25%}` у head-хуку) — менеджерам був замалий. Іконки — ТІЛЬКИ Heroicons (бібліотека, що йде з Filament), інлайн-SVG, жодних іконкових шрифтів (FontAwesome у старій CRM) і жодних сторонніх бібліотек: для нових сторінок брати `heroicon-o-*`. Власні SVG (значок, іконка виходу) — теж інлайн.

## Принцип UX: «де змінюєш — там і зберігається»

**Жодних загальних кнопок "Зберегти" в інтерфейсі.**

Кожна зміна зберігається одразу в тому місці, де вона відбувається:

- **Select, Toggle, DatePicker** — `->live()` → зміна моментально потрапляє в Livewire і одразу зберігається в БД через `updated()` хук.
- **TextInput, Textarea** — `->lazy()` → зберігається при виході з поля (blur), не на кожен символ.
- **Складні дії** (upload файлу, прив'язка рахунку тощо) — через модальне вікно зі своєю кнопкою підтвердження всередині.

В `EditRecord`-сторінках обов'язково:
```php
protected function getFormActions(): array { return []; } // прибирає Save/Cancel знизу

public function updated(string $name): void {
    if (! str_starts_with($name, 'data.')) return;
    try {
        $this->save(shouldRedirect: false, shouldSendSavedNotification: false);
    } catch (\Illuminate\Validation\ValidationException) {}
      catch (\Throwable) {}
}
```

## Конвенції

- UI — українською. Код, коментарі в коді — англійською, з поясненням **чому**, не що (Filament-синтаксис самоочевидний).
- **Грошові суми — завжди у фінансовому форматі, тисячні відділяються пробілом** (явна вимога користувача). Виведення: `number_format($v, ..., '.', ' ')` / `->money('UAH', locale: 'uk')`. Поля вводу: маска `->mask(RawJs::make("\$money(\$input, '.', ' ')"))` + `->stripCharacters([' ', ','])` + `->numeric()` — зразок: поле "Сума" у Settlements і Payments. Кожне нове поле суми робити так само.
- `ClientResource` свідомо без бізнес-логіки (без угод/замовлень) — "просте відображення" за прямим запитом, розширення — окрема майбутня задача.
