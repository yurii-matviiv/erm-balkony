# Планувальник завдань (cron → Laravel Schedule)

Єдине місце, де описано, **як в ERM запускаються фонові завдання**. Перед тим як вигадувати новий cron, скрипт чи чергу — читай цей файл і користуйся описаним способом.

## Як це влаштовано

```
cron (раз на хвилину)  →  php artisan schedule:run  →  routes/console.php  →  artisan-команди
```

1. На хостингу є **один** запис crontab (його вже налаштовано, нічого додавати не треба):
   ```
   * * * * * cd ~/balkony-vikna.kyiv.ua/erm && /usr/local/php84/bin/php artisan schedule:run >> /dev/null 2>&1
   ```
   PHP-бінарник хостингу: `/usr/local/php84/bin/php`.
2. `schedule:run` — це і є «головний скрипт-диспетчер». Він сам вирішує, які завдання зараз мають спрацювати, за розкладом із `routes/console.php`.
3. Кожне завдання — окрема artisan-команда (`app/Console/Commands/`). Нове завдання = нова команда + один рядок у `routes/console.php`. **Crontab не змінюється ніколи.**

### Чому немає окремого «легкого» PHP-скрипта перед Laravel

Така ідея розглядалась (скрипт без Laravel перевіряє БД і будить Laravel лише за потреби). Відмовились: `schedule:run` і так запускається щохвилини для вже наявних завдань (`sync:legacy`, `conversions:run` тощо), тому Laravel стартує щохвилини в будь-якому разі, а другий скрипт лише додав би дубль логіки і ще одне місце, що може зламатися. Економія досягається інакше — див. «Правила» нижче (раннє завершення команди). Повертатися до цієї ідеї має сенс, тільки якщо колись `schedule:run` перестане запускатися щохвилини.

## Наявні завдання (routes/console.php)

| Команда | Розклад | Примітка |
|---|---|---|
| `sync:legacy --scheduled` | кожні 5 хв | виходить одразу, якщо автосинк вимкнено тумблером; пише heartbeat `sync_scheduler_tick_at` (сторінка синхронізації червоніє, якщо його нема понад 15 хв). Локально його запускає завдання Windows, див. `docs/arch/sync-legacy.md` |
| `conversions:run` | кожні 15 хв | виходить одразу, поки mode = off |
| `audience:run` | щодня 03:22 | Customer Match |
| `ads:sync-stats` | щодня 04:10 | статистика Google Ads |
| `reminders:dispatch` | щохвилини | push-нагадування менеджерам, у т.ч. про заміри (див. нижче) |

## Як додати нове завдання

1. Створити команду: `php artisan make:command НазваКоманди` (клас у `app/Console/Commands/`, `$signature = 'область:дія'`).
2. У `handle()` **спершу дешева перевірка, чи є що робити** (один запит з індексом або перевірка тумблера) і `return self::SUCCESS;`, якщо нічого. Важка робота — тільки після цього.
3. Додати в `routes/console.php`:
   ```php
   Schedule::command('область:дія')
       ->everyFiveMinutes()      // або dailyAt('03:22') тощо
       ->withoutOverlapping()    // не запускати другий екземпляр, поки перший працює
       ->runInBackground();      // не затримувати інші завдання цієї хвилини
   ```
4. Додати рядок у таблицю «Наявні завдання» вище.
5. Перевірити локально: `php artisan область:дія`, потім `php artisan schedule:list`.
6. Після деплою нічого на хостингу робити не треба (cron вже тікає щохвилини).

## Правила

- **Раннє завершення.** Команда, що запускається часто (щохвилини), мусить без роботи завершуватись за кілька мілісекунд: один запит по індексу, і `return`. Саме це дає «майже нуль навантаження», коли подій немає.
- **Ідемпотентність.** Повторний запуск (збій, ручний запуск) не має дублювати результат. Для подій — позначка «оброблено» (`notified_at` тощо), яка ставиться **після** успішної дії, а не до неї.
- **`withoutOverlapping()` і `runInBackground()`** — для всіх завдань, крім миттєвих.
- **Мінуси розкладу.** Завдання, що не мусять бути «о 00:00», ставимо на «непарну» хвилину (03:22, 04:10), щоб вони не збігалися з 5/15-хвилинними.
- **Тумблер, якщо завдання можна вимкнути.** Налаштування в `app_settings` + `--scheduled`-прапорець, як у `sync:legacy`: команда тихо виходить, поки вимкнено.
- **Помилки.** Не ковтати мовчки: логувати (`Log::warning/error`) з контекстом; невдалу спробу лишати необроблено і обмежувати кількість повторів.
- **Час.** Розклад Laravel іде за `app.timezone` (зараз UTC), а не за київським часом. Для `dailyAt()` враховуй це або став `->timezone('Europe/Kyiv')`.
- **Не запускати довгі процеси** (демони, `queue:work`, `schedule:work`) на хостингу: фонові процеси там зупиняються. Усе, що довге, розбивається на короткі запуски з розкладу.

## Push-нагадування (`reminders:dispatch`)

Реалізовано (`app/Console/Commands/DispatchReminders.php`), щохвилини, `withoutOverlapping` + `runInBackground`. Використовує той самий `WebPushSender`, таблицю `push_subscriptions` і `/sw.js`, що й кнопка «тестове сповіщення».

- Один дешевий запит; якщо нічого не настало — завершується одразу.
- **Час.** `manager_reminders.reminder_datetime` — київський «настінний» час (так його вводять менеджери), тому «настало» порівнюється з `now('Europe/Kyiv')`, а не з UTC. Нагадування, прострочені більш ніж на добу, не відправляються (захист від старих записів із `sync:legacy`).
- `kind='lead'` (звичайні, вкладка «Заявки»): один push; `notified_at` ставиться після успішної відправки (є підписки й відправлено, або підписок немає зовсім); невдача повторюється, максимум 5 спроб.
- `kind='measurement'` (вкладка «Заміри»): push, потім повтор кожні `repeat_interval_minutes`, не більше `max_repeats` повторів, доки менеджер не натисне «Побачив» (`acknowledged_at`) або не позначить «Виконано».
- Правила заміру (години, повтори) — лише в `config/measurement_reminders.php`; інструкція на сторінці «Нагадування → Заміри» (іконка ?) будується з цього конфігу.

## Тестування і діагностика

```
php artisan schedule:list        # що і коли запуститься
php artisan schedule:test        # інтерактивно запустити одне завдання
php artisan schedule:work        # ⚠️ лише на «чистій» локальній базі без продакшн-даних: запускає ВСІ завдання (конверсії в Google, push). З продакшн-копією не запускати
```
На хостингу: перевірити, що завдання виконуються, можна за логом `storage/logs/laravel.log` та за полями «останній запуск» самих команд (де вони є).
